# Tracker 第三阶段 3.1：本地活动账本与派生状态可靠性

## 本批目标

本批先修复“学习动作已经保存，但 XP、等级、连续学习或热力图发生漂移”的基础问题，再建立一个可回放、可对账且不影响旧数据的影子活动账本。账本当前不是业务真相源；单词、练习、计时、日记、计划、成就与连续学习各自的 Zustand Store 仍是正式数据源。

## 数据链路

每个受支持的学习动作按同一口径处理：

1. 写入或修改所属业务 Store；
2. 以记录编辑前后的“绝对应得值”计算 XP 差值；
3. 对热力图贡献执行新增、跨日期移动或删除；
4. 写入带实体、版本、幂等键、before/after 和派生影响的影子事件；
5. 通过基线加事件回放，核对 XP、等级、热力图、当前/历史最长连续天数和打卡日期。

当前覆盖：

- 单词记录：新增、数量/日期编辑、删除；
- 模考记录：新增、时长/日期编辑、删除；
- 计时记录：新增、秒级时长/日期编辑、删除；
- 学习日记：新增、日期编辑、删除；
- 计划执行：创建、完成/取消完成、删除及删除计划时的子执行清理；
- 每日打卡：学习前后均可领取，同日只奖励一次，连续 7 天奖励只计算一次；
- 统计页访问：React StrictMode 下单次页面进入只计一次。

## 兼容旧数据的启动策略

- 新存储键为 `ielts-tracker:activityLedger`，schema/persist version 均为 `1`。
- 首次升级只读取当前 XP、等级、连续学习、热力图、最后打卡日和已完成计划日期，建立轻量 checkpoint。
- 不枚举、复制或改写既有单词、练习、计时、日记正文和备注；旧数据不会被重新奖励 XP，也不会因初始化被覆盖。
- 已有 ledger 基线时启动直接跳过，不重复回填。
- 旧版不一致的 `level`、`currentStreak` 和 `lastActiveDate` 在水合时按 XP/热力图生成运行时投影；不会为了初始化账本批量改写业务记录。

## 容量与失败隔离

- 账本只保存 checkpoint 之后的变更事件，不复制完整旧数据库。
- 事件窗口上限为 500 条；到达上限后先回放为新的 checkpoint，再从 revision 1 开始记录后续事件。
- ledger 的读取、写入、替换与 append 均为 shadow failure-isolated：配额不足或存储不可用时记录会继续保留在业务 Store，应用启动和学习动作不会因账本失败而中断。
- 持久化数据在水合时检查 schema、baseline 和 event 基本结构；损坏的影子数据会被隔离，不用于业务状态。

## XP、连续学习与幂等修正

- 单词和模考不再按“变化量单独四舍五入”，而是用编辑前后整条记录各自应得 XP 的差值，确保新增后删除回到原值。
- 计时记录明确按秒换算 XP；编辑和删除使用同一绝对规则。
- 删除、跨日期编辑与取消计划完成会同步减少或移动热力图贡献。
- `totalXP` 不允许低于 0，等级始终由 XP 阈值派生；旧备份导入时也会归一化。
- `longestStreak` 是历史峰值。回放会按事件逐步保留峰值，不会因后续删除记录而抹去历史最长连续天数。
- 连续 7/30 天学习可由任意真实学习活动解锁对应里程碑，不再要求额外点击每日打卡。
- 3.1 的 ledger checkpoint 曾临时承载历史打卡阻断；3.2 已将该职责迁移到正式的 `dailyCheckins` 数据，ledger 只保留对应影子投影。

## 备份与恢复边界

- 公开 Backup V2 继续只包含正式业务数据，不包含影子 ledger，也不包含 API Key；3.2 新增正式 `dailyCheckins` 字段并兼容缺少该字段的旧备份。
- 成功导入后，ledger 从导入后的正式数据重新建立 `source=import` checkpoint；导入前的本地 shadow 事件不会混入新数据。
- 导入失败时，现有回滚机制会恢复导入前的正式业务快照，并为恢复后的数据重新建立 checkpoint。
- V2 导入新增同一集合 ID 唯一性校验，防止重复 ID 导致一次查找却多条更新/删除的派生状态错误。

## 当前明确不做

- ledger 还不是 source of truth，不会在启动时用回放结果覆盖业务 Store。
- 徽章列表和 `statsViewCount` 暂未进入事件流；回放只保证 XP/level、streak/heatmap 和 check-in 投影。徽章仍按里程碑单向解锁。
- 3.2 已为日常学习动作加入短期 undo journal；全量导入、清空和多标签页串行化仍是后续独立门槛。
- Backup V2 回滚保证正式业务数据恢复，但 ledger 会重建为 checkpoint，不保留原 shadow 事件历史。
- 事件只按本机 append 顺序回放；乱序合并、跨设备冲突、Supabase 同步和管理员审计均不在 3.1 范围。
- 计划触发的每日打卡奖励是不可逆的独立里程碑；之后取消或删除计划只撤销计划本身的活跃贡献，不收回已领取的每日 XP/徽章。
- 领域徽章检测仍有异步 reconciliation 改造空间；本批只把连续学习徽章接入同步主链路。

## 发布影响

- `Frontend`: changed；新增本地持久化契约、活动事件、派生状态修正、备份导入重建与集成测试。
- `Backend`: reviewed-not-needed；本项目本批仍仅使用浏览器 localStorage，没有 Supabase、远程同步、RPC、RLS 或认证变化。
- `Admin`: reviewed-not-needed；该 tracker 没有 `/admin`，本批没有远程管理员可见状态。
- `Deployment`: not-deployed；修改只保留在本地分支，没有提交、推送或部署。

## 验收清单

- TypeScript、oxlint、Vitest 与生产构建全部通过。
- 旧数据 checkpoint 不改变正式业务 Store，也不复制正文/备注。
- Word、Practice、Timer、Diary 的 create → edit/move → delete 全链路回放与实时投影一致。
- 手动打卡不受当天先前学习动作抑制；多个计划同日完成只奖励一次。
- 历史已完成计划在导入重建后仍阻止重复打卡奖励。
- ledger 配额写入失败不会阻断正式记录、XP 或热力图更新。
- 事件超过上限后自动 rebase，回放结果保持一致。
- 真实 browser adapter 成功导入会重建 ledger；中途写入失败会恢复正式业务快照。

## 下一阶段建议

3.2 已实现事务日志、启动恢复、正式打卡幂等和只读一致性诊断。下一步进入 3.3：收口 storage adapter，为批量导入/清空增加跨重启原子方案和多标签页锁，再准备本地 outbox 与远程同步契约。
