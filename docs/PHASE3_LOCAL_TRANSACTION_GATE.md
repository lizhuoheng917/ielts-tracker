# Tracker 第三阶段 3.2：本地事务恢复与一致性诊断

## 本批目标

本批解决“一个学习动作同时修改记录、XP、连续学习和打卡状态时，页面恰好关闭可能留下半套数据”的问题。正式业务数据仍由各领域 Zustand Store 保存；新增的事务检查点只在一次写入过程中短暂存在，影子活动账本仍只用于回放和诊断。

## 正式数据与影子数据

- 正式数据：单词、模考、计时、日记、计划执行、XP/等级、连续学习/热力图、设置，以及新增的 `ielts-tracker:dailyCheckins`。
- `dailyCheckins` 是“某天是否已经领取打卡奖励”的正式幂等记录；活动账本不再负责阻止重复发奖。
- 影子数据：`ielts-tracker:activityLedger`。它可以删除并从正式数据重新建立，不进入公开备份，也不能覆盖正式数据。
- 短期恢复数据：`ielts-tracker:mutationJournal`。它只保存本次变化涉及的实体和字段，不复制无关记录或完整数据库。

## 事务写入顺序

受保护的学习动作使用同一流程：

1. 先用纯函数计算业务记录、XP、等级、热力图、连续天数和打卡状态的目标值；
2. 写入并读回校验 `phase=prepared` 的最小 undo checkpoint；
3. 同步写入所有正式 Store；
4. 从 localStorage 读回校验正式数据是否等于预期；
5. 将 checkpoint 标记为 `phase=committed`；
6. 补写影子活动账本，并验证账本事件确实持久化；
7. 删除 checkpoint。

checkpoint 首次写入失败时，不允许开始任何正式数据写入。空间不足时只会先删除可重建的影子账本再重试；仍失败则拒绝本次动作。

当前覆盖：

- 单词、模考、计时、日记记录的新增、编辑和删除；
- 计划执行的新增、完成/取消完成、删除，以及删除计划时对子执行的清理；
- 手动每日打卡；
- 完成计划与同日首次打卡奖励在同一个根事务中完成，不再嵌套两次跨 Store 写入。

仅修改一个 localStorage key 的设置项、计时器运行态和计划标题/启停不需要跨 Store checkpoint。

## 启动恢复

`main.tsx` 不再静态导入 App 或 Store。启动先运行不依赖任何 Store 的 raw-storage 恢复器，恢复完成后才动态加载 React 应用，避免 Zustand 在半写状态下提前水合。

- 没有 checkpoint：正常启动。
- `prepared`：逐 patch 接受“尚未写入”或“已经写成预期值”两种状态，并统一恢复到操作前；恢复再次中断时保留 checkpoint，下次启动继续。
- `committed`：保留已经成功的正式数据，删除可能不完整的影子账本并从正式 Store 重建。
- 当前值既不是 before 也不是 expected-after：视为未知并发写入，停止自动恢复并显示安全页，不盲目覆盖数据。
- 每日打卡旧数据迁移属于正式幂等契约；若它无法安全持久化，应用会暂停进入，而不是带着重复发奖风险继续运行。

## 打卡和备份兼容

- 新安装和旧用户会建立 `dailyCheckins`；已有完成计划和 `lastCheckinDate` 会转成 `source=migration`、`awardedXP=0` 的历史阻断记录，不重复补发 XP。
- 公开 Backup V2 新增 `dailyCheckins` 字段，但仍接受缺少该字段的旧 V2，并在导入前生成兼容记录。
- V1 缺少字段时执行相同迁移，不继承当前设备上与备份无关的打卡记录。
- 新版备份显式提供空数组时保持为空，不擅自推断用户意图。
- 导出使用字段白名单；mutation journal、影子 ledger、API Key 和其他运行时附加字段均不会进入 JSON。
- 设置页会串行化导入与清空；备份文件读取期间禁用其他数据操作，离开页面会取消尚未完成的读取，避免旧回调在清空或导航后重新写回数据。

## 只读一致性诊断

设置页提供活动一致性入口。诊断以活动账本基线加事件回放，并与当前正式数据比较：

- XP 与等级；
- 当前/历史最长连续天数、最后活跃日与逐日热力图计数；
- 最后打卡日和已奖励日期集合。

诊断结果只有“一致、发现差异、暂不可用”，不提供自动修复按钮。徽章和统计页访问次数不参与本批对账。运行诊断前后，正式 Store、影子 ledger 和 localStorage 必须逐字节不变。

## 故障测试

故障注入使用同一持久化 Map 模拟重启，并覆盖：

- prepared 后在首个、中间和最后一个正式 key 写入后崩溃；
- 恢复过程再次中断，随后重试和第三次 no-op；
- committed 后账本尚未写完；
- 全新浏览器尚未持久化默认 Store key 时的首次写入恢复；
- 旧持久化 key 缺少新字段时保持原始磁盘形状，不把 Zustand 运行时默认值误写回去；
- 未知并发第三值；
- checkpoint 持久化失败时零正式写入；
- 配额不足时删除可重建账本后重试；
- journal 只包含变化实体和字段，不复制大型无关集合；
- 缺少 `dailyCheckins` 的 V1/V2 导入迁移及公开导出边界。
- 正式打卡幂等迁移无法持久化时阻止进入应用。

## 当前明确边界

- 影子账本仍不是 source of truth，也不会自动修复正式数据。
- 浏览器 localStorage 没有 compare-and-swap；当前通过 pending journal 和第三值冲突检测避免盲目覆盖，但尚未提供真正的多标签页串行锁。
- JSON 全量导入和“一键清空”是破坏性批量操作，仍使用现有的校验、同进程回滚和重载流程；它们尚未获得跨页面崩溃原子性。clear 的前缀清理不得删除 pending journal。
- Backend、跨设备同步、认证、管理员审计和远程冲突解决尚未接入。

## 下一阶段建议

进入 3.3“存储适配与批量原子操作”：把 Store 对 localStorage 的直接依赖收口到 repository/storage adapter，为导入和清空增加 IndexedDB staging 或 generation pointer，并用 Web Locks 串行化多标签页写入。在这一层稳定后，再接入 Supabase Auth、Postgres/RLS 和本地 outbox，同一领域命令才可以安全地在本地与后端之间同步。
